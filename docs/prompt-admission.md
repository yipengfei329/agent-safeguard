# 消息提交与恢复授权（0.2.2）

## 问题

0.2.1 用同一个 `grant` 标记表示“有一条安全用户输入”并阻止下一条输入。标记只在根轮次 `turn.start` 被消费。若输入被当前轮次或下游处理器接收，没有对应的新根轮次，标记会残留；后续正常消息持续收到 `recovery.busy`。

这一状态不一定伴随敏感命中、扫描异常或活动工具，因此状态命令可能同时报告 `active`、`blocked=false` 和 `lastRule=null`。只观察这些字段不足以证明可以继续。

已在纯状态机、原生 Mods 和真实宿主的合成下游处理场景中复现。实际用户实例没有保留完整的提交事件轨迹，不能确定它具体由哪一次下游处理或轮次交错触发。SDK 流输入的真实回放会先等待前一轮结束，再触发下一次 `prompt.submit`；该路径不代表桌面 composer 的轮次中输入行为。

## 修复

1. **提交互斥按本次调用管理。** 通过检查后创建独立 ticket，`next()` 尚未完成时拒绝并发提交。`finally` 在成功、下游拒绝和异常时释放本次 ticket；迟到回调不能清除别的提交。
2. **普通输入不产生恢复授权。** 初始轮次已有的行为无需额外 grant。没有新 `turn.start` 的普通消息以及正常轮次中的补充消息都不会留下忙碌标记。
3. **恢复授权仅在空闲入口发放。** 恢复后只允许通过完整检查的可信输入在旧轮次、调用、子代理及提交全部结束时授权下一次根轮次。宿主声明的 `next()` 契约是空闲提交开始轮次后返回；授权由该轮次消费，或在提交结束时作废。未知自动根轮次不能继承未使用的授权。
4. **明确排队边界。** 恢复后的轮次仍在执行时，composer 中途提交或排队会收到 `recovery.wait`，应等待本轮结束再提交。现有 Mods 接口没有把中途提交与某个未来根轮次关联的标识，本版不猜测关联，也不以提示词文本识别身份。SDK 已在外层排队、直到空闲才发出 hook 的输入按正常空闲入口处理。
5. **状态说明可核验。** `/agent-safeguard-status` 增加 `promptAdmission`：`submitting`、`awaitingTurn`、`activeTurns`、`activeAgents`。只含布尔值和计数，不输出消息内容。`recovery.busy` 明确说明前一次提交尚未结束，不再把它描述为敏感信息拦截。

扫描规则、100 ms 预算、上下文污染门禁、故障健康检查和旧工具身份隔离保持原有约束。不会重放被扣留的结果，也不会撤销已经执行的工具。

## 验证

- 纯状态新增 13 项：无轮次提交、轮次中消息、真正未完成的提交、旧 ticket 迟到、未消费恢复授权、非可信输入、恢复后的中途提交及上下文门禁。
- 原生 Mods 新增 4 项，恢复相关文件合计 31 项通过。原有一个模拟改为在 `prompt.submit` 返回之前发出 `turn.start`，与类型声明及真实 SDK 跟踪一致，原来的模型请求次数断言保留。
- `npm run test:admission` 的 6 个真实 Claude Code 2.1.325 场景：普通跟进、无模型轮次的下游处理、下游拒绝、下游异常及健康检查、恢复后无轮次处理、SDK 排队。捕获本地模型桩的实际请求，确认被扣留的虚构凭据未进入请求。
- 同一合成处理场景对照 0.2.1，能复现安全跟进被 `recovery.busy` 拦下；新版安全跟进成功。
- 原有 26 项实际请求恢复矩阵和 7 项 Write 超时恢复场景通过。
- 完整核心/CLI 测试 2,696 项、完整原生 Mods 测试 155 项、Rust release 测试 17 项通过；插件验证通过。

完整工具拦截路径测量覆盖 10 KB、100 KB、约 1 MB、约 4 MB 输出，8/100/1,000 条规则及 1/4 并发，包含正常输出与 IP 脱敏。48 组中 33 组完成采样，15 组触发 `inspection.timeout`；不为未完成组报告成功延迟分位数。逐组 p50/p95/p99、输出大小、规则数和并发数见 [测量数据](prompt-admission-measurements.json)。这次修改没有解决大文本/高负载扫描超时，不能把原生功能测试通过等同于所有性能负载达标。

临时测试插件才包含下游处理的故障注入；正式安装文件不包含注入。测试仅使用合成消息、文件和规则，不复制用户项目、日志、会话内容或真实敏感信息。真实 SDK 验证不代替所有桌面事件顺序、其他插件组合及远端 MCP 验收。

## 已运行实例

升级磁盘文件不等于旧实例已经换成新版。宿主的普通或强制 `/reload-plugins` 在已观察到的实例中未重建 Mods 状态，不能据“Reloaded”文字宣布恢复。安装后需要核对实际实例版本及提交状态；必要时由宿主重新打开原会话，保留原历史，不通过关闭检测或清空历史解锁。
